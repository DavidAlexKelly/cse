# Wire contract for the tasks this bridge sends

The byte-level contract for NETN v4 tasking, with golden vectors. Written to be
implemented against by a federate in any language, so that "we both read the
spec" can be replaced by "we both pass these vectors".

It exists because the failure mode between two independent implementations of the
same FOM struct is not an error. Both sides are confident, one is misaligned or
misreading units, and the only symptom is a simulated entity that quietly does
nothing.

- Vectors are generated by `tools/wire_vectors.py`, deliberately an independent
  implementation rather than a dump of our encoder — if the two agree, the
  encoding is corroborated twice.
- Our encoder is held to them by `HlaEncoderTest`, which runs in the Docker
  build.
- `bridge_preview_move_task` prints the same fields for any live request, so a
  real call can be compared against this document.

## Encoding rules

From IEEE 1516-2010 §4.13.9, unchanged in 1516-2025 (HLA 4):

| Construct | Encoding |
|---|---|
| Primitives | **Big-endian.** `MeterFloat64` = IEEE 754 float64, `*Float32` = float32, `*Enum32`/`EpochTime` = int32, `*Enum8` = one octet, `TimeMillisecondInt64` = int64 |
| `HLAfixedRecord` | Before **each field**, pad to that field's own octet boundary, measured from the start of the record. **No trailing padding.** A record's boundary is the maximum of its fields' |
| `HLAvariableArray` | 4-byte `HLAinteger32BE` element count, then before **each element**, pad to the element's octet boundary. With a 24-byte, 8-aligned element this means **4 bytes of padding after the count** |
| `UUID` | `HLAfixedArray` of 16 `HLAbyte` — 16 raw bytes in RFC 4122 order, octet aligned, no count prefix, **not text** |

Alignment is measured **from the start of the encoded value**, which is why a
decoder that carries only a sliced buffer cannot compute it. See
`interop/HlaAlignedCodec.cs`.

## The units trap

`LocationStruct` is `{X, Y, Z}` `MeterFloat64` in the IEEE 1278.1-2012 §1.6.3
**world coordinate system**: geocentric ECEF metres. It is **not** latitude and
longitude, despite the name, and NETN-BASE has separate `GeodeticPoint` and
`GeodeticCircle` types for values that are. We misread this ourselves in early
analysis; assume the other end may have too.

`DirectionDegreesFloat32` is **degrees** clockwise from true north in [0,360).
The v2-era `AngleRadianFloat32` was radians, so code ported from v2 is out by
57.29578.

## Golden vectors

Reference point: **latitude 60.476, longitude 25.116, altitude 500 m** (WGS-84),
which is

```
ECEF X = 2853356.7941 m
ECEF Y = 1337581.7704 m
ECEF Z = 5527238.2030 m
```

Hex below is exact for these inputs. A one-bit difference in the last mantissa
place is not a conformance failure — `cos`/`sin` are permitted to differ by 1 ulp
between platforms — so compare the **decoded metre values to within 1e-6**, and
treat lengths and field offsets as strict.

### A. `LocationStruct` — 24 bytes

```
41 45 C4 F6 65 A4 DA 41  41 34 68 ED C5 36 C1 ED  41 55 15 B1 8C FD 3D 16
└──────── X ──────────┘  └──────── Y ──────────┘  └──────── Z ──────────┘
```

### B. `MagicMoveTaskStruct` — 28 bytes

`{Location, Heading}` with heading 270.0 degrees:

```
41 45 C4 F6 65 A4 DA 41 41 34 68 ED C5 36 C1 ED 41 55 15 B1 8C FD 3D 16 43 87 00 00
└─────────────────────── Location (0..23) ──────────────────────────────┘ └ Hdg ─┘
```

`43 87 00 00` is 270.0f. If a receiver reads that as radians it will point the
entity somewhere meaningless without erroring.

### C. `MoveToLocationTaskStruct` — the one with an open question

`{Location, Path, MoveType, Speed}` with an empty `Path`, `MoveType` = 0
(CrossCountry) and `Speed` = 30.0 m/s. The standard's wording is genuinely
ambiguous about whether an **empty** variable array carries the padding that
would precede a first element, and implementations differ:

| Reading | Length | `Speed` at |
|---|---|---|
| Empty `Path` is 4 bytes (count only) | **36** | offsets 32..35 |
| Empty `Path` padded to 8 | **40** | offsets 36..39 |

```
36-byte form:
41 45 C4 F6 65 A4 DA 41 41 34 68 ED C5 36 C1 ED 41 55 15 B1 8C FD 3D 16
00 00 00 00 | 00 00 00 00 | 41 F0 00 00
  count=0      MoveType=0     Speed=30.0

40-byte form:
… same 24 bytes of Location …
00 00 00 00 | 00 00 00 00 | 00 00 00 00 | 41 F0 00 00
  count=0      padding        MoveType=0    Speed=30.0
```

**Why this specific ambiguity is dangerous.** A decoder that omits the padding
while the sender includes it reads `MoveType` from the padding — zero, which is a
valid enumerator (CrossCountry) — and `Speed` from `MoveType`, which is also
zero. So the task decodes "successfully" with a plausible move type and a speed
of zero, and a receiver honouring `Speed = 0` literally holds the entity
stationary. Accepted, unmoved, nothing logged.

**How to resolve it:** call `bridge_preview_move_task` against a running bridge
and read `TaskParameters.lengthBytes`. That is the RTI's own encoder answering,
which is the only authority that matters. Then fix this document to state the
single correct form.

### D. `LocationStructArray`, 3 elements — 80 bytes

Where the padding is unambiguous, and where an omitted `Align` shows up:

```
offsets 0..3    00 00 00 03    element count
offsets 4..7    00 00 00 00    padding, so the first element starts 8-aligned
offsets 8..31   41 45 C4 86 …  element[0]
…
total           4 + 4 + 3 x 24 = 80
```

A decoder that reads elements straight after the count consumes the padding as
the first four bytes of `element[0].X` and is 4 bytes out for the rest of the
array. Affects `Path` on patrol, and the `Area` field of `IndirectFire`,
`CreateObstacle` and `DisruptCommunication`.

## Inherited parameters on every task

Sent alongside `TaskParameters`, each as its own interaction parameter:

| Parameter | Type | Notes |
|---|---|---|
| `Entity` (NETN-SMC) | `UUID` | The entity to task. 16 raw bytes |
| `TaskId` | `UUID` | Identifies the task |
| `UniqueId` (NETN-BASE) | `UUID` | Identifies the interaction. **We set it equal to `TaskId`**, because `SMC_Response.Action` references this and not `TaskId` |
| `SendTime` (NETN-BASE) | `EpochTime` | int32 seconds since the Unix epoch |
| `TaskMode` | `TaskModeEnum8` | One octet. 0 non-concurrent, 1 concurrent |
| `Annotation` | `HLAunicodeString` | 4-byte character count then UTF-16BE |
| `Tasker` | `UUID` | **Omitted** unless `TASKER_UUID` is configured — the FOM default is "commander undefined", which is honest, whereas a fabricated UUID claims an entity that does not exist |

`StartTime` is omitted so its documented default applies: the current `SendTime`,
i.e. immediately.

## Acknowledgement

Please send one. Without it, "accepted" and "silently ignored" are the same
observation from our side.

| Interaction | Parameters | Meaning |
|---|---|---|
| `ETR_TaskStatus` | `Task` (UUID), `TaskStatus` (`TaskStatusEnum32`) | 0 Accepted, 1 Refused, 2 Cancelled, 3 Executing, 4 Completed, 5 Error |
| `SMC_Response` | `Action` (UUID = the task interaction's `UniqueId`), `Status` (`HLAboolean`, 4 bytes) | NETN-SMC requires a response to **every** entity control action, supported or not |

Also worth publishing: the NETN-SMC `BaseEntity` attribute `SupportedActions`, an
`HLAvariableArray` of `EntityControlActionEnum` (int32). It lets a tasker check
before sending rather than inferring from silence. `MoveToLocation` is 28,
`MagicMove` 10, `Patrol` 33, `ChangeSpeed` 36, `ChangeHeading` 40.

## Checklist for a receiving implementation

1. Read big-endian.
2. Carry an absolute offset and align before every record field and array element.
3. Treat `LocationStruct` as geocentric ECEF metres; convert to geodetic yourself.
4. Treat `DirectionDegreesFloat32` as degrees.
5. Treat `Speed = 0` as "sender expressed no preference", not "stand still".
6. Tolerate an empty `Path` — the destination is in `Location`.
7. Respond with `ETR_TaskStatus` or `SMC_Response`.
8. Assert vectors A, B and D above in a unit test; add C once its length is
   settled.
